# 로컬 답변 생성 연결

## 목표

검색 화면에서 관련 원문을 먼저 보여주고, 사용자가 원할 때만 생성 모델이 답변을 정리하도록 했다. 외부 API 비용 때문에 기본 검색 흐름까지 생성 모델에 의존시키지는 않았다.

## 선택

- 실행 도구: Ollama
- 모델: `qwen3:4b-instruct` Q4_K_M, 약 2.5GB
- 호출 주소: `127.0.0.1:11434`
- 입력: 검색 상위 원문 2개, 최대 5,000자
- 출력: 짧은 답변 1개, 원문 인용, 질문에 포함된 학교급·학년·날짜 확인

`qwen3:4b` 최신 태그는 4B Thinking 모델을 가리켜 답변 대신 긴 판단 과정을 출력했다. 웹 서비스에는 같은 크기의 Instruct 태그를 사용했다.

## 안전장치

`/api/search`는 생성 모델을 호출하지 않는다. 사용자가 `자료로 답변 만들기`를 눌렀을 때만 `/api/answer`가 검색을 다시 실행한다. 브라우저가 보낸 원문을 신뢰하지 않고 서버가 검색한 자료만 모델에 전달한다.

모델 출력은 그대로 표시하지 않는다. 출처 ID가 이번 검색 결과에 있는지, 인용문이 해당 문서 필드의 연속된 원문인지, 모든 답변 문장에 본문 인용이 있는지를 기존 `answer_packet` 검증으로 확인한다. 검증이 실패하면 답변을 숨기고 원문 검색 결과는 유지한다. 이 검사는 인용 문자열의 출처만 확인하며 답변 의미가 정확하다는 보장은 아니다.

## 로컬 측정

MacBook Air M2, 메모리 16GB에서 확인했다. Codex 실행 환경에서는 Metal 명령 큐를 만들 수 없어 CPU로 강제 실행했다.

| 경우 | 시간 | 비고 |
|---|---:|---|
| 짧은 단일 자료 답변 | 8.08초 | 모델 최초 로딩 5.39초 포함 |
| 기존 전체 스키마, 원문 3개 | 81.43초 | 입력 3,207토큰, 출력 235토큰 |
| 축약 스키마, 원문 2개 | 45.49초 | 입력 1,868토큰, 출력 200토큰 |

CPU 기준 45초는 빠르지 않다. 화면에서는 생성 중 상태를 따로 표시하고 검색 입력을 잠시 잠근다. 일반 Ollama 앱에서 Apple Silicon Metal을 사용할 때의 지연 시간은 별도로 다시 측정해야 한다.

설치 후 모델 폴더는 약 2.3GB, 사용자 폴더에 임시로 둔 Ollama 앱은 약 599MB였다. Thinking 모델은 검증 뒤 삭제해 모델 두 개가 중복으로 남지 않게 했다.

## 검증

- Python 단위·HTTP 테스트 98개 통과
- 실제 Dense 검색 → `/api/answer` → Qwen3 → 원문 인용 검사 통과
- 브라우저에서 생성 버튼, 진행 상태, 답변, `자료 2` 버튼의 원문 이동 확인
- 브라우저 콘솔 오류 없음

JavaScript 단위 테스트는 이 작업 환경에서 Node 실행 파일을 찾지 못해 다시 실행하지 못했다. 대신 실제 브라우저에서 새 `app.js` 로드와 상호작용을 확인했다.
