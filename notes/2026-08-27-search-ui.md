# 로컬 검색·근거 확인 화면

## 목적과 범위

비용 제약을 반영해 유료 생성 API 없이 질문을 검색하고 원문 근거를 확인하는 화면을 만들었다. 기존 원문 질문 → body-only Dense 순위를 유지했다. 이번 변경은 검색 순위 개선 실험이 아니며, 검색 성능이 향상됐다고 주장하지 않는다.

구현 파일은 `src/search_app.py`, `web/index.html`, `web/app.css`, `web/app.js`, `tests/test_search_app.py`다. 기존 평가셋·청크·임베딩과 앞선 검색문 실험은 변경하지 않았다.

## 사용자 흐름

1. 질문을 입력하거나 네 가지 예시 중 하나를 선택한다.
2. 기본 5개 검색 결과의 문서명·구조 경로·본문 미리보기·유사도 점수를 확인한다.
3. 결과를 선택하면 전체 청크 본문을 읽는다. 점수는 정답 확률이 아니다.
4. 질문 조건 문구가 본문·경로·문서명 중 어디에 존재하는지 확인한다. 문구 일치는 의미나 적용 범위를 검증하지 않는다.
5. 필요한 경우 원문을 복사하거나 JSON으로 다운로드한다. 서버가 질문·결과를 자동으로 파일에 저장하지는 않는다.

q008처럼 요청 날짜를 본문·경로에서 찾지 못한 경우 경고를 표시한다. 질문이 요구하는 모든 근거를 회수했는지 판정하는 기능은 없으며, q006 등의 검색 누락도 기존과 같다. 생성 답변은 표시하지 않는다.

## 비용·노출 범위

- 웹 서버는 생성기를 호출하지 않으며 `/api/generate` 같은 경로를 제공하지 않는다. 키가 환경에 있어도 사용하지 않는다.
- 기존 로컬 BGE-m3 캐시를 사용하고 새 모델을 다운로드하지 않는다.
- Python 표준 라이브러리 HTTP 서버와 HTML/CSS/JavaScript만 추가했다. 외부 폰트·CDN은 없다.
- `127.0.0.1` 전용 서버이며 외부 인터페이스 바인딩을 거절한다. 공개 배포용은 아니다.
- 허용한 정적 파일 세 개만 제공한다. `.env`, 소스 코드, 임의 파일 경로는 제공하지 않는다.
- 다른 Host·Origin 요청을 거절하고, JSON 요청·크기·질문 길이를 검사한다. 모델 동시 실행은 잠금으로 제한한다.
- 질문은 POST 본문으로 보내고 요청 로깅을 비활성화한다. 결과 응답은 `no-store`다. 사용자가 다운로드한 JSON에는 질문과 문서 본문이 포함된다.
- 문서명·경로·본문은 `textContent`로 렌더링하며 원문 HTML을 실행하지 않는다. 추가 방어로 CSP를 설정했다.

## 확인한 것

- 전체 Python 테스트 **52개 통과**: 이전 42개 + 검색 서비스/HTTP 테스트 10개.
- JavaScript 구문 검사 통과.
- 실제 서버에 HTTP로 q001~q013을 전송해 **13개 검색 성공**.
- 고정 기준선이 있는 답변 가능 질문 11개는 **top-5 청크 순서가 모두 일치**.
- 실제 q008 응답에서 `2028년 3월 1일` 날짜 근거 미확인 경고 필드를 확인.
- 13개 응답 모두 `generation_called=false`, `answer=null` 확인.
- 잘못된 JSON, 과도한 요청, 잘못된 Host/Origin, 파일 경로 접근, 생성 경로 접근 거절을 테스트.

HTTP 점검의 요약 결과는 `experiments/search_app_smoke.json`에 저장한다.

## 아직 확인하지 못한 것

내장 Browser 자동화 도구가 `failed to write kernel assets` 오류로 시작되지 않았다. 별도 로컬 Chrome 검증도 브라우저 프로세스가 시작 직후 종료되어 실행하지 못했다. 따라서 **실제 브라우저의 화면 배치, 버튼 클릭, 클립보드, 다운로드, 모바일 화면, HTML 주입 시 렌더링 동작은 아직 검증 완료로 보고하지 않는다.**

현재 검증은 Python 테스트·실제 HTTP 요청·JS 구문 검사·코드 검토다. 화면 캡처나 성공한 브라우저 테스트 결과를 대체 자료로 만들지 않았다. 사용자가 로컬 주소를 열어 확인할 수 있도록 서버를 실행했고 앱에 브라우저 패널 열기를 요청했다.

## 실행

저장소 루트에서 `uv run python src/search_app.py`를 실행한 뒤 `http://127.0.0.1:8765/`에 접속한다. 별도 API 설정이나 결제가 필요 없다. 서버를 직접 실행한 터미널에서 Ctrl+C로 종료한다.

다음 점검은 브라우저에서 한글 글자 수 예시 → 결과 선택 → 시행일 예시 → 경고 확인 순서다. 실제 화면에서 확인된 문제가 있으면 먼저 수정한 뒤 검색 성능 개선 실험을 이어간다.

## 2026-09-01 원문 PDF 페이지 연결

- 파싱할 때 실제 PDF 페이지 경계를 기록하고 섹션·검색 단위까지 전달했다.
- 기존 1,331개 검색 단위의 ID·순서·본문·경로가 모두 동일함을 비교한 뒤 청크 색인 지문만 갱신했다. 임베딩은 다시 만들지 않았다.
- 결과 카드와 읽기 화면에 `168쪽`, `214~215쪽` 같은 페이지 범위를 표시한다. 복사·텍스트 저장에도 페이지가 포함된다.
- `원문에서 확인하기`는 검색 자료로 등록되고 로컬에 실제 파일이 있는 PDF만 제공한다. 임의 파일 경로와 경로 순회 요청은 404로 거절한다.
- Python 테스트 58개와 JavaScript 테스트 5개, 총 63개가 통과했다.
- 실제 Dense 검색으로 한글 바이트 질문의 첫 결과가 중학교 기재요령 168쪽에 연결되는 것을 확인했다.
- 내장 브라우저에서 검색 → `168쪽` 표시 → `원문에서 확인하기` 클릭 → PDF `#page=168` 새 탭 열기까지 확인했다.

브라우저 DOM과 클릭 흐름은 확인했지만 모바일 화면 배치와 픽셀 단위 시각 검수는 별도 점검 대상으로 남긴다. 서버는 계속 로컬 개발용이며 외부 배포는 하지 않았다.
