# 검색·생성 회귀 평가 분리

## 문제

개별 실패 질문을 고친 뒤 다른 질문이 나빠지는지 바로 확인할 한 명령이 없었다. 검색 실패와 생성 실패도 화면에서는 모두 “답변을 만들지 못함”으로 보여 원인 구분이 어려웠다.

## 변경

`eval/run_eval.py`가 13문항을 읽어 두 점수표를 별도로 만든다.

- 검색: Hit@K, 근거 그룹 Recall@K, Complete@K, MRR@10, p50·p95 지연
- 생성: 답변 가능 문항 성공률, 답변 불가 문항 거절률, 전체 과제 성공률, 원문 인용 유효성, p50·p95 지연

여러 학교급 문서에 같은 규정이 복제된 경우에는 문서별 청크를 모두 맞혀야 한다고 채점하지 않는다. 같은 주장을 뒷받침하는 대체 청크를 하나의 근거 그룹으로 보고, 여러 근거 그룹이 필요한 질문은 `Complete@K`로 확인한다.

생성 인용 평가는 모델이 선택한 근거가 실제 원문의 같은 위치인지 다시 확인한다. 이는 문자열 출처 검증이며 답변 문장 전체의 의미적 함의를 검증한 수치는 아니다.

## 검색 기준선

2026-09-10 운영 검색 경로를 top-10으로 실행한 결과다. 답변 불가 2문항은 검색 정답 청크가 없으므로 검색 평균에서 제외하고 생성 거절 평가에 포함한다.

| 지표 | 결과 |
|---|---:|
| Recall@1 | 0.4545 |
| Recall@5 | 0.8182 |
| Recall@10 | 0.8636 |
| Complete@5 | 0.8182 |
| MRR@10 | 0.6364 |

q006은 필요한 초등학교·중학교 근거 중 하나만 top-10에 들어왔고 q008은 정답 근거가 top-10 밖이었다. 이후 검색 변경은 이 기준 파일과 비교하며, 핵심 지표가 낮아지면 실행을 실패시킨다.

## 생성 안정성 점검

Ollama 호출은 이미 JSON Schema를 `format`에 전달하고 `temperature=0`을 사용한다. 모델은 원문을 다시 복사하지 않고 근거 번호만 반환하며 프로그램이 번호를 원문 위치로 복원한다. 따라서 이 설정을 중복 변경하지 않고 회귀 테스트에서 유지 여부를 검사했다.

동시 생성은 즉시 503을 반환하던 잠금을 최대 20초 동안 순서대로 기다리는 제한 대기열로 바꿨다. 대기 인원과 실행 여부는 `/api/info`에 표시한다. 20초 안에 차례가 오지 않으면 무한 대기를 막기 위해 503을 반환한다.

Ollama가 꺼졌거나 지정 모델이 없을 때 13개 연결 실패를 생성 성능 0점으로 저장하지 않도록 실행 전 확인도 추가했다. 이번 생성 기준선은 Ollama가 실행되지 않은 상태였으므로 기록하지 않았다.

## 보류한 변경

- Dense 점수만으로 생성 차단: q002처럼 점수는 낮지만 답할 수 있는 질문도 함께 차단해 운영 기본값으로 쓰지 않았다.
- CrossEncoder 상시 적용: 기존 실험에서 MRR은 올랐지만 Complete@5는 같았고 문항 하나가 회귀했으며 CPU 지연이 컸다.
- LLM 쿼리 재작성: 검색 호출마다 생성 지연과 새 실패 지점을 추가하므로 현재 기준선에서 별도 실험한 뒤 결정한다.
